## 1. ФУНДАМЕНТ: КАК GOOGLE ХРАНИТ ВЕСЬ ИНТЕРНЕТ

Google не хранит интернет в виде отдельных файлов на диске. Вся система разбита на 5 технологических слоев:

```
┌──────────────────────────────────────────────────────────────┐
│  СЛОЙ 5: СЕРВИСНЫЙ (Search Serving / RankBrain / MUM / Gemini)│
├──────────────────────────────────────────────────────────────┤
│  СЛОЙ 4: ИНДЕКСАЦИЯ (Alexandria / Percolator — Realtime Index)│
├──────────────────────────────────────────────────────────────┤
│  СЛОЙ 3: ВЫЧИСЛЕНИЯ (MapReduce ──► FlumeJava / MillWheel)    │
├──────────────────────────────────────────────────────────────┤
│  СЛОЙ 2: БАЗЫ ДАННЫХ (Bigtable / Spanner — NoSQL / NewSQL)    │
├──────────────────────────────────────────────────────────────┤
│  СЛОЙ 1: РАСПРЕДЕЛЕННАЯ ФАЙЛОВАЯ СИСТЕМА (Colossus / GFS)    │
└──────────────────────────────────────────────────────────────┘
```

## 2. ПОШАГОВЫЙ ПАЙПЛАЙН: ОТ КРАУЛЕРА ДО ВЫДАЧИ ЗА 0.02 СЕКУНДЫ

### 1. Краулер (Googlebot) — Сбор Сети
* Миллионы легковесных краулеров (на базе кастомного headless Chromium) круглосуточно сканируют интернет.
* Они исполняют динамический JavaScript, кликают по SPA и сохраняют сырой отрендеренный DOM в **Bigtable** (колоночная база данных).
* Страница сжимается (Snappy/Brotli) и получает уникальный хэш `DocID` (64-битный ключ).

### 2. Слой Хранения: Colossus (GFS 2.0)
* Данные разбиваются на блоки (chunks) по **64 МБ** и дублируются на сотни тысяч серверов с Reed-Solomon кодированием (защита от выхода из строя целых дата-центров).

### 3. Индексация в реальном времени: Percolator (Замена классического MapReduce)
* **Раньше (MapReduce):** Google раз в сутки пересчитывал весь интернет огромным батчем (занимало 12–24 часа).
* **Сейчас (Percolator):** Транзакционная система на базе Bigtable с распределенными блокировками. 
  * Как только страница изменилась, обновляется **только этот кусочек инвертированного индекса** за миллисекунды.

### 4. Шардирование Инвертированного Индекса (Inverted Index Sharding)
Инвертированный индекс Google (миллиарды слов $\to$ миллиарды `DocID`) не поместится ни в один сервер.
* **Шардирование по документам (Document Sharding):**
  * Весь массив `DocID` делится на тысячи «сегментов» (Shards).
  * Каждый шард обслуживается отдельным кластером машин (Index Servers), держащих индекс **целиком в оперативной памяти (RAM / SSD)**.
* **Шардирование по терминам (Term Sharding):**
  * Для редких и сверхчастотных терминов создаются многоуровневые словари.

### 5. Архитектура Запроса (Search Serving Tier)
Когда ты вбиваешь запрос в Google:
1. Запрос прилетает на **Root Server** (балансировщик).
2. Балансировщик рассылает запрос **одновременно на тысячи шардов (Index Servers)**.
3. Каждый шард за 5 миллисекунд ищет совпадения среди своих миллионов документов и возвращает локальный `Top-100` кандидатов.
4. **Scoring / Resonance Stage:**
   * Серверы агрегации (Gatherer) объединяют кандидатов.
   * Модели машинного обучения (RankBrain, PageRank, BERT/MUM) пересчитывают релевантность.
5. Финальный `Top-10` отправляется пользователю. Весь процесс занимает **~15–30 миллисекунд**!

## 3. СРАВНЕНИЕ: ПОЧЕМУ POLER-ENGINE ИСПОЛЬЗУЕТ ТЕ ЖЕ ПРИНЦИПЫ GOOGLE

| Принцип Google | Реализация в Google (Дата-центры) | Реализация в POLER-Engine (Локальный ПК) |
|---|---|---|
| **Zero-Retention RAM** | Данные хранятся в Bigtable/Colossus, в память поднимаются только активные шарды | 3-проходный стриминг `mmap` + `Zero-Copy &str` (память $O(\text{vocab})$) |
| **Top-K Pruning** | Шард отсекает слабые документы на лету через бинарные кучи | `BinaryHeap` с монотонным ключом `bit_key(f64)` в Pass 2 |
| **Realtime Updates** | Percolator инкрементально обновляет изменившиеся страницы | Watcher-режим `--watch` с трекингом `mtime/size` |
| **Дисковый кэш символов** | Spanner / Bigtable | `sqlite_store.rs` (B-Tree таблица символов на диске) |
| **Bypass JS / SPA** | Headless Chrome рендеринг внутри Googlebot | Запланированная интеграция Chromium CDP |
