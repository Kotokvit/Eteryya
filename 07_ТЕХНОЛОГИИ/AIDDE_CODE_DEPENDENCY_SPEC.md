# 🧠 АРХИТЕКТУРА AI-INTERPRETED DEPENDENCY ENGINE (AIDDE)
## Почему линейный интерпретатор, grep и RAG бессильны на 30 млн строк кода

---

## 1. СУТЬ ПРОБЛЕМЫ: ПОЧЕМУ ВСЕ СУЩЕСТВУЮЩИЕ ИНСТРУМЕНТЫ ЛОМАЮТСЯ

Ты вскрыл фундаментальную инженерную боль, о которую разбиваются все современные AI-агенты и senior-разработчики:

1. **Слепота grep / ripgrep / RAG:**
   * Находят имя функции `process_payload()`. 
   * Не видят: кто передал туда мутабельный указатель, какой глобальный флаг изменился в 50-м модуле и почему без этой строчки упадет микросервис на проде через 3 дня.
2. **Линейная тупость компилятора / интерпретатора (Single-Fault Blindness):**
   * Компилятор/интерпретатор работает **жадно и линейно**: падает на первой ошибке (например, `Type Mismatch: expected String, got &str`).
   * Ты фиксишь тип. Интерпретатор делает шаг вперед и падает на второй ошибке (`NullPointer / Borrow Mut`).
   * Ты фиксишь вторую — ломается третья, четвертая, десятая.
   * **Почему?** Потому что интерпретатор проверяет *локальную корректность инструкции*, но **не видит архитектурной интенции (зачем эта функция вообще здесь стоит)**.

## 2. АЛГОРИТМ: ИНТЕРПРЕТИРУЕМЫЙ ГРАФ ПОТОКА ДАННЫХ И ИНТЕНЦИИ (AIDDE)

Чтобы AI мог уверенно переписать или отрефакторить 30 млн строк кода без эффекта домино, инструмент должен строить **3-мерный сквозной граф (Semantic Semantic-Causal Graph)**:

```
                      [ ИСХОДНЫЙ КОД: 30 млн строк ]
                                     │
                                     ▼
        ┌────────────────────────────────────────────────────────┐
        │  УРОВЕНЬ 1: Нативный AST & Symbol Resolver             │
        │  (Rust rustc / Python ast / Clang libclang / Tree-sitter)
        └────────────────────────────┬───────────────────────────┘
                                     │
                                     ▼
        ┌────────────────────────────────────────────────────────┐
        │  УРОВЕНЬ 2: Dynamic / Static Data-Flow Graph           │
        │  (Def-Use Chains + Call Graph + Side-Effect Tracker)   │
        └────────────────────────────┬───────────────────────────┘
                                     │
                                     ▼
        ┌────────────────────────────────────────────────────────┐
        │  УРОВЕНЬ 3: Impact Analysis & Intention Matrix          │
        │  (Что сломается в других файлах, если удалить функцию) │
        └────────────────────────────┬───────────────────────────┘
                                     │
                                     ▼
                     [ AI-Ready Dependency Subgraph ]
                     (Субъект → Сайд-эффект → Зависимости)
```

## 3. ИЗ ЧЕГО СОСТОИТ АЛГОРИТМ

### Шаг 1. Symbol Resolution & Inter-File Linker (Cross-File Scope)
Вместо текстового поиска по строкам движок парсит AST каждого файла и строит **Глобальную Таблицу Символов (Global Symbol Table)**:
* `File_A.rs :: struct Session` $\longleftrightarrow$ импортирован в `File_B.rs` как `use crate::File_A::Session`.
* Движок точно знает уникальный ID каждого символа: `uuid(crate::auth::Session::validate)`.

### Шаг 2. Def-Use Chains (Цепочки определения и использования)
Алгоритм отслеживает жизненный цикл данных:
1. **Где создана переменная/память?** (Origin)
2. **Кто ее мутировал?** (Mutators)
3. **Кто читает результат?** (Consumers)
4. **Какие системные сайд-эффекты она вызвала?** (Сетевой сокет, запись в диск, мьютекс).

### Шаг 3. Two-Way Impact Analysis (Двунаправленный анализ влияния)
Когда AI запрашивает рефакторинг функции `fn foo()`:
* **Upstream Graph (Кто зависит от меня):** Показывает все 400 файлов и 1200 функций, которые сломаются, если изменить сигнатуру или логику `foo()`.
* **Downstream Graph (От кого завишу я):** Показывает все скрытые глобальные переменные, конфиги и неявные импорты, которые нужны `foo()` для работы.

### Шаг 4. Semantic Contract Validation (Проверка интенции)
Движок через интерпретатор/компилятор прогоняет **Символьное выполнение (Symbolic Execution)**:
* Не просто «компилируется ли код?», а:
  $$\text{Invariant}(f) = \forall x \in \text{Inputs} \implies \text{PreCondition}(x) \land \text{PostCondition}(f(x))$$
* Если AI переписывает функцию, движок сразу выдает: *«Ты удалил параметр `timeout`, но в файле `network/socket.rs:142` этот параметр ожидает непустое значение таймера, иначе сокет зависнет в deadlock»*.

## 5. ВЫВОД
Интерпретатор проверяет **букву закона** (синтаксис и типы).
`poler-engine` с графом зависимостей проверяет **дух закона** (архитектуру, потоки данных и связи между всеми 30 миллионами строк). 
Объединение AST-парсера компилятора + графа K-hop потока данных уничтожает галлюцинации и ошибки рефакторинга на корню!
